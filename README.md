# Чат с ИИ

Одностраничный веб-чат с языковой моделью через OpenRouter. Next.js (App Router) + TypeScript.

Ответ приходит потоком. Генерацию можно остановить кнопкой или Esc. 429, таймаут и обрыв
сети показываются понятным текстом с кнопкой «Повторить». История живёт до закрытия вкладки,
ответы рендерятся как markdown, есть тёмная тема. Всем можно пользоваться с клавиатуры.

## Запуск

Нужен Node.js 22.18+ (или 23.6+): тесты запускают `.ts`-файлы встроенным в Node
TypeScript без сборки.

```bash
npm install
cp .env.example .env.local
npm run dev
```

В `.env.local` впишите свой ключ с https://openrouter.ai/keys в `OPENROUTER_API_KEY`. В
`OPENROUTER_MODEL` уже стоит бесплатная модель. Если OpenRouter её убрал из каталога,
возьмите любую другую с суффиксом `:free`. Затем откройте http://localhost:3000.

Тесты парсера стрима: `npm test`. Запускаются встроенным `node --test`, без Jest и Vitest.

Как убедиться, что ключ не уходит в браузер: во вкладке Network есть только запросы на
`/api/chat` к своему серверу, а `openrouter.ai` там не появляется. Ключ читается только в
`app/api/chat/route.ts` через `process.env` без префикса `NEXT_PUBLIC_`, поэтому в клиентский
бандл Next его не включает.

## Структура

```
app/api/chat/route.ts   прокси до OpenRouter: валидация, стрим, отмена, таймаут
app/chat.tsx            чат: состояние, отправка, стоп, ошибки, история
app/message.tsx         одно сообщение, markdown для ответов модели
app/page.tsx            подключает чат только на клиенте
lib/chat.ts             запрос к прокси, разбор SSE, классификация ошибок
lib/chat.test.ts        тесты разбора SSE
lib/history.ts          чтение и запись истории в sessionStorage
```

## Ключевые решения

- Next.js вместо отдельного бэкенда. Ключ OpenRouter нужен только на сервере, и Route Handler
  `app/api/chat` закрывает это без второго проекта. NestJS рассматривал, но для одного
  прокси-эндпоинта модули и DI ничего не дают.
- Прокси `POST /api/chat` отдаёт SSE-поток OpenRouter без изменений. Сервер не парсит стрим:
  клиенту всё равно нужно разбирать `data:`-строки, а ошибки посреди генерации OpenRouter
  присылает в том же формате. Лишний слой преобразования был бы ещё одним местом для багов.
- `req.signal` пробрасывается в запрос к OpenRouter. Когда пользователь жмёт «Стоп» или
  закрывает вкладку, генерация обрывается и у провайдера, а не только на клиенте, и квота
  бесплатной модели не тратится впустую.
- Таймаут 30 секунд стоит только на ожидание заголовков ответа. Длинный ответ может
  стримиться дольше, и обрывать его по общему таймеру было бы неправильно.
- Сервер проверяет тело запроса: принимаются только роли `user` и `assistant` (других UI не
  создаёт), не больше 50 сообщений и не длиннее 32 000 символов каждое. Прокси открыт, и без
  этих лимитов через него можно было бы гонять что угодно за мой ключ. Поле ввода ограничено
  8000 символами через `maxLength`, а лимит сервера выше, потому что ответ модели бывает
  длинным. Когда лимит был 8000 на всё, первый же длинный ответ ломал следующий запрос (400).
  Клиент отправляет только последние 20 сообщений, поэтому длинный диалог в лимит сервера
  тоже не упирается.
- Стрим читается через `fetch` и `ReadableStream`, а не через `EventSource`: тот умеет только
  GET и не принимает тело запроса с историей. SSE-строки разбирает `readDeltas` в
  `lib/chat.ts`. Он буферизует неполные строки между чанками и декодирует байты с
  `{ stream: true }`, иначе русская буква, разрезанная между чанками, превращается в `�`.
  Оба случая покрыты тестами.
- Список сообщений — это `<section aria-live="polite">` с `aria-busy`, пока идёт генерация.
  Без `aria-busy` скринридер начал бы зачитывать ответ по кусочкам на каждый токен, а так он
  прочитает его целиком, когда стрим закончится. Индикатор «печатает» вынесен из этой
  области в отдельный `role="status"`, чтобы `aria-busy` его не глушил.
- «Стоп» — это `AbortController`. Его сигнал обрывает `fetch` в браузере, а сервер через
  `req.signal` обрывает запрос к OpenRouter. Уже пришедший текст остаётся в истории с
  пометкой «Ответ остановлен» и уходит в контекст следующего запроса.
- Esc слушается на `window`, а не на поле ввода: остановить генерацию должно быть можно
  откуда угодно, где бы ни стоял фокус. Обработчик висит только пока идёт генерация.
- «Отправить» и «Стоп» — одна и та же кнопка, у которой меняются подпись и `type`. Если бы
  это были две разные кнопки, при переключении фокус с нажатой пропал бы в `body`, и
  клавиатурному пользователю пришлось бы искать его заново. После остановки фокус
  возвращается в поле ввода. По той же причине кнопка не становится `disabled` при пустом
  поле: отключённый элемент теряет фокус. Пустое сообщение просто не отправляется.
- Ошибки сведены к четырём видам (`ChatError.kind`), у каждого свой текст для человека:
  - `rate-limit` — 429 от OpenRouter, как в ответе на запрос, так и посреди стрима
    (бесплатные модели так делают);
  - `timeout` — 504 от прокси, если модель не прислала заголовки за 30 секунд, или 45 секунд
    без единого нового токена на клиенте. Второй таймер нужен на случай, когда соединение
    живо, но стрим завис;
  - `network` — `fetch` не дошёл до сервера или соединение оборвалось посреди стрима;
  - `server` — всё остальное, с текстом от сервера.
- В любом из этих случаев индикатор гаснет, кнопка возвращается в «Отправить», а рядом с
  текстом ошибки появляется «Повторить». Если до ошибки успел прийти кусок ответа, он
  остаётся с пометкой «Ответ прервался из-за ошибки», а при повторе заменяется новым ответом.
  Повтор отправляет ту же историю заново, вводить сообщение ещё раз не нужно.
- История хранится в `sessionStorage`. Она переживает перезагрузку и случайный F5, но
  пропадает, когда вкладка закрыта. В задании сказано «в рамках сессии», а `sessionStorage`
  ровно так и работает. `localStorage` я не взял: переписка с моделью может быть личной, и
  хранить её в браузере бессрочно, никого не спросив, неправильно. Для этого нужны явная
  кнопка «сохранять историю» и управление ею, что за рамками задачи. Сервер историю не
  хранит вообще. Кнопка «Новый диалог» очищает и экран, и хранилище.
- Если перезагрузить страницу посреди генерации, недописанный ответ сохранится с пометкой
  «Ответ остановлен», как после нажатия «Стоп». Иначе после перезагрузки обрывок выглядел
  бы как полный ответ.
- Чат рендерится только на клиенте (`next/dynamic` с `ssr: false`). История живёт в
  `sessionStorage`, которого на сервере нет. При серверном рендере первый кадр был бы
  пустым, и сохранённый диалог пришлось бы подставлять эффектом после гидрации: лишний
  рендер и мигание пустого состояния. Теперь история читается сразу в инициализаторе
  `useState`. SEO для чата не важно, а без JS он всё равно не работает.

## Интерфейс

- Светлая и тёмная темы переключаются по системной настройке (`prefers-color-scheme`), все
  цвета заданы переменными в `:root`. Отдельный переключатель не делал: для одного экрана
  чата системной настройки хватает.
- До первого сообщения показывается пустое состояние: подсказка по клавишам (Enter,
  Shift+Enter, Esc) и три примера запросов. Пример отправляется одним нажатием, так что
  попробовать чат можно, ничего не печатая.
- На телефоне: высота через `100dvh`, чтобы поле ввода не пряталось под панелью браузера;
  отступы учитывают safe-area (вырез и полоска «домой»); у поля шрифт 16px, иначе iOS
  приближает страницу при фокусе; кнопки не ниже 44px. Проверял на 375px и 320px:
  горизонтальной прокрутки нет.
- Поле ввода растёт вместе с текстом через `field-sizing: content`, но не выше 40% экрана.
  В браузерах, где это свойство не поддерживается, поле остаётся в одну строку с прокруткой.
  JS для авторазмера ради этого не писал.
- Анимация «модель печатает» отключается при `prefers-reduced-motion`.
- Ответы модели рендерятся как markdown через `react-markdown` и `remark-gfm` (таблицы,
  списки, код). Сообщения пользователя остаются обычным текстом: то, что человек набрал,
  должно показываться как есть. Сырой HTML из ответа `react-markdown` по умолчанию не
  вставляет, а ссылки с `javascript:` вычищает. Проверял оба случая на ответе с
  `<img onerror>` и такой ссылкой: ничего не выполнилось. Внешние ссылки открываются в
  новой вкладке с `rel="noopener noreferrer"`.
- Элемент сообщения обёрнут в `memo`. Во время стрима меняется только последний ответ,
  остальные сообщения сохраняют ту же ссылку на объект, и markdown всей истории не
  парсится заново на каждом токене.
- Блоку кода дан `tabIndex={0}`: длинная строка прокручивается по горизонтали, и без фокуса
  с клавиатуры до этой прокрутки не добраться. Лигатуры в коде отключены, чтобы `=>` не
  превращалось в `⇒`.

## Где я сделал не так, как просили

**Обводка фокуса.** В задании просят убрать стандартный `outline` у кнопок и поля ввода,
потому что в разных браузерах он выглядит по-разному. Но в том же задании есть требование,
чтобы интерфейсом можно было полноценно пользоваться с клавиатуры и ходить по нему Tab.
Если просто убрать обводку, человек с клавиатуры перестанет видеть, где сейчас фокус, и
второе требование сломается (это ещё и WCAG 2.4.7 Focus Visible, уровень AA).

Поэтому стандартную обводку я убрал, но заменил своей, одинаковой во всех браузерах:

- у кнопок `:focus-visible` с `outline: 2px solid` акцентного цвета и отступом 2px. Он
  появляется только при навигации с клавиатуры, а при клике мышью его нет, так что вид не
  портится;
- у поля ввода своей обводки нет, вместо неё подсвечивается весь блок ввода вместе с кнопкой
  (`.composer:has(textarea:focus)`). Для текстовых полей браузеры считают фокус видимым даже
  после клика мышью, и обводка вокруг одной textarea внутри рамки смотрелась бы лишней;
- индикатор сделан через `outline`, а не через `box-shadow`. В режиме высокой контрастности
  Windows (`forced-colors`) тени не рисуются, а `outline` остаётся;
- контраст обводки с фоном не ниже 3:1 в обеих темах.

Жалоба на разнобой между браузерами снята, а доступность с клавиатуры осталась.

## Что бы я сделал дальше

- Ограничить частоту запросов к прокси (по IP или по сессии). Сейчас `/api/chat` открыт, и
  лимиты на размер тела не мешают кому угодно тратить мою квоту OpenRouter.
- Умная автопрокрутка. Сейчас на каждом новом токене список прокручивается вниз, даже если
  человек отмотал вверх и читает старый ответ. Правильно прокручивать, только когда он и так
  был внизу, а иначе показывать кнопку «вниз».
- E2E-тесты на Playwright для стрима, «Стопа» и всех видов ошибок с подменой ответа
  `/api/chat`. Сейчас тестами покрыт только парсер SSE, а остальное я проверял руками в
  браузере с подменённым `fetch`.
- Учитывать `Retry-After` при 429 и показывать, сколько подождать, вместо «подождите минуту».
- Кнопка «Скопировать» у блоков кода и у ответа целиком.
- Выбор модели из списка бесплатных и ручной переключатель темы.

## ИИ-лог

Работал в Claude Code (модель Claude Opus).
Архитектуру решал я. ИИ предлагал отдельный Node-сервер, я предложил Next с Route Handler, Пушбек про `outline` тоже мой. ИИ дополнил его деталями про `forced-colors`, про то, что у `textarea` `:focus-visible` срабатывает и при клике мышью, и про контраст 3:1. ИИ писал часть кода и документацию.

Где ИИ ошибался и как это заметили:

- Написал разбор стрима через `TextDecoderStream`, и `tsc` упал на несовпадении типов
  lib.dom. Заменили на `TextDecoder` с `{ stream: true }` и добавили тест на русскую букву,
  разрезанную между чанками, чтобы эту деталь нельзя было сломать незаметно.
- Поставил в прокси лимит 8000 символов на любое сообщение, не подумав, что ответ модели
  бывает длиннее. Первый же длинный ответ сделал бы следующий запрос невалидным (400). Сам
  заметил это, когда разбирал ошибки: разделили лимиты для ввода и для сервера и стали
  отправлять только последние 20 сообщений.
- Загружал историю через `setState` в `useEffect`. Линтер React 19
  (`react-hooks/set-state-in-effect`) на это указал. Перешли на рендер только на клиенте и
  чтение истории в инициализаторе `useState`.
- После «Повторить» фокус с клавиатуры пропадал в `body`: кнопка исчезала вместе с блоком
  ошибки. Нашлось при прогоне Tab/Shift+Tab в браузере, теперь фокус возвращается в поле.
- В первой версии CSS у `textarea` появилась бы собственная обводка поверх подсветки блока
  ввода, потому что для текстовых полей `:focus-visible` срабатывает всегда. Поймали при
  перечитывании стилей до проверки в браузере.
